# 앱 전환 후 간헐적 키보드 하단 잘림 조사

사용자 관찰: 다른 앱으로 전환하고 키보드를 열었을 때 낮은 빈도로 발생한다.

## 현재 판단

앱 전환 시 IME 창 위치와 하단 인셋 갱신의 불일치가 우선 조사 대상이다. 현재 코드와 과거 시험 기록에서 관련 단서는 확인했지만, 이번 사용자 증상의 근본 원인은 아직 확정하지 못했다.

### 코드에서 확인한 내용

- `KeyboardView.kt:91`의 인셋 리스너는 `getInsets(systemBars())`의 하단 값을 기본 4dp 패딩에 더한다. 다음 전달값이 0이면 이전 하단 여백을 즉시 제거한다.
- `MinjjImeService.onStartInputView()`는 기존 키보드를 다시 바인딩한다. 재표시 시점의 인셋 재요청이나 창 위치 검사는 없다. 명시적인 `requestApplyInsets()`는 새 클립보드 패널을 붙일 때만 호출한다.
- `KeyboardFrame.onMeasure()`는 키보드의 측정 높이를 그대로 사용한다. 시스템 창 자체의 화면 위치가 어긋난 경우에는 내부 재측정만으로 그 위치를 교정하지 못한다.
- 키보드의 행 높이는 실제 높이 제한이 아닌 configuration의 `screenHeightDp`를 기준으로 계산한다. 실제 가용 높이가 더 작아지는 별도 상황에서는 고정 높이 행이 잘릴 가능성이 있으나, 이번 앱 전환 증상과의 연관성은 확인하지 못했다.

인셋이 0이라는 사실만으로 결함이라고 판단할 수는 없다. 내비게이션 UI가 숨겨져 있거나 상위 View에서 이미 공간을 확보한 경우에도 0이 올 수 있다. `getInsetsIgnoringVisibility()`로 무조건 교체하거나 과거 최대 여백을 계속 유지하면 불필요한 여백 또는 중복 여백이 생길 수 있다. API의 현재/비가시 상태 인셋 구분은 [Android WindowInsets 문서](https://developer.android.com/reference/android/view/WindowInsets#getInsetsIgnoringVisibility(int))를 참고한다.

### 과거 기록에서 확인한 내용

`RealImeTest.native()`에는 접근성 키 좌표와 실제 View 좌표가 다르면 키보드를 숨겼다가 다시 표시하는 복구 코드가 이미 있다. 이 복구는 제품 코드가 아니라 시험 준비 코드에만 있다.

예를 들어 `device-runs/20261106-175649-7ce508a5/screens/ime-position.txt`에는 세 시나리오 모두 재표시 전 92px, 재표시 후 0px의 차이가 기록돼 있다. 다른 2026-11-06 기록에는 160px 차이도 있다. 해당 기기는 iPlay60 mini Turbo, Android 14/API 34다.

이 기록은 창 전환과 연관된 좌표 불일치가 실제 시험에서 관찰됐다는 근거다. 다만 과거 파일에는 당시 하단 인셋 및 터치 좌표 실측값이 없어서, 화면 표면의 이동과 접근성 좌표 캐시를 구분하거나 80 Turbo의 이번 증상과 동일하다고 단정할 수는 없다. 기존 시험은 자동 복구 후 진행되므로 최종 통과 결과만으로 첫 표시가 정상이라고 판단해서도 안 된다.

## 추가한 진단 시험

`RealImeTest.appSwitchFirstShowKeepsImeGeometryAndSafeArea()`를 추가했다.

- 시스템 설정 앱과 로컬 입력 fixture 사이를 전환한다. fixture로 돌아온 첫 표시에서는 기존 `native()`의 숨김/재표시 복구를 호출하지 않는다.
- 접근성 키 좌표와 View 좌표를 비교한다.
- DOWN/CANCEL 터치를 이용해 실제 입력 표면과 View 좌표의 차이를 검사한다. 텍스트를 입력하거나 수집하지 않는다.
- 편집기 애니메이션 대기 후의 첫 터치 차이를 보존하고, 350ms 뒤 다시 측정해 전환 중 이동과 지속적인 어긋남을 구분한다.
- 현재/비가시 상태의 시스템 인셋, 하단 패딩, 마지막 행, 상위 View의 위치와 높이를 기록한다.
- 마지막 행이 키보드 내부 패딩과 화면의 시스템 안전 경계 위에 있는지 검사한다.
- 실패 시 fixture 화면만 캡처한다. 기존 스크립트가 환경설정, 이전 IME, 회전 설정을 복원한다.

## 검증

- 80 Turbo `T860128GB26388620671`, Android 16/API 36.
- 1차: 세로 방향 앱 전환 30회 통과. 모든 표본에서 하단 인셋 105px, 하단 패딩 114px, 화면/터치 좌표 차이 0px. 114px는 105px에 기본 4dp의 정수 환산값 9px를 더한 값이다.
- 1차 결과: `device-runs/20261108-114840-T860128GB26388620671/`.
- 중간 실행 `device-runs/20261108-115026-T860128GB26388620671/`: 기존 터치 보정 도우미의 두 번째 확인에서 기대 2240px / 수신 2232px로 실패했다. 두 표본 사이에 8px 차이가 발생했지만, 실패 전 원시 표본을 모두 기록하지 못했으므로 지속적인 창 이동 또는 하단 잘림의 증거로 취급하지 않는다. 이후 진단은 보정 대신 단일 원시 표본을 기록하도록 변경했다.
- 중간 실행 `device-runs/20261108-115218-T860128GB26388620671/`: 시험 준비 단계에서 현재 fixture 편집기와 IME 연결을 확인하지 못해 종료됐다. 앱 전환 검증을 수행하지 못한 실행이다. APK 교체 후 남은 서비스 연결 가능성을 고려해 다음 실행 전 디버그 앱을 종료했다.
- 최종 `device-runs/20261108-115319-T860128GB26388620671/`: 세로 15회 / 가로 15회 통과. 하단 인셋 105px, 패딩 114px로 유지됐고, 모든 표본에서 초기/안정화 후 터치 차이와 접근성 좌표 차이는 0px였다. 마지막 행은 세로 2446px / 안전 경계 2455px, 가로 1486px / 안전 경계 1495px로 각각 9px 위에 배치됐다. 최종 가로 화면 캡처도 확인했다.

완료된 두 실행의 총 60회에서 하단 잘림은 재현되지 않았다. 이는 드문 문제가 없다는 증명이 아니다. 이번 시험은 시스템 설정 앱과 fixture 사이의 전환이며, 사용자가 증상을 본 두 앱의 정확한 조합, 전체 화면 모드, 태스크바 상태, 전환 중 표시 요청 타이밍을 모두 재현하지는 않는다.

## 원인을 확정하는 데 필요한 구분

1. 하단 인셋이 존재하는데 키보드 패딩이 반영되지 않았다면, 인셋 전달/재적용 경로를 수정한다. 상위 View가 이미 확보한 공간을 함께 확인해야 한다.
2. 패딩과 행 배치가 정상인데 실제 터치 좌표 또는 화면 표면만 이동했다면, 앱 전환 중 IME 창 위치/애니메이션 제어 문제를 조사한다. 패딩 증가로 해결하려 하면 위치 오류를 가릴 수 있다.
3. 마지막 행 자체가 측정 높이를 넘는다면, 실제 가용 높이에 맞춰 행 높이를 제한해야 한다.

제품에서 재발 순간을 잡을 때는 입력 내용 없이 위 기하 정보와 인셋 전달 시각만 수집하는 것이 적절하다. 현재 조사에서는 제품의 표시 동작을 변경하지 않았다.
